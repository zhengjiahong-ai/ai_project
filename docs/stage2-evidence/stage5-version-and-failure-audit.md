1. 已保存正文A，原有历史正文B和空正文。编辑未保存草稿D后恢复B：服务器保存B，并将A及D分别保留为已保存版本和未保存草稿版本，原来源1项保留。收据 `stage5-version-restored-runtime.json`。

3. 编辑冲突草稿E后，由另一个HTTP客户端保存正文F。原浏览器保存返回版本冲突，服务端任务与F完全未变；刷新后E仍在，界面可展开F核对。截图 `stage5-draft-conflict-browser.jpg`，权威基准 `stage5-conflict-authoritative.json`。
4. 明确点击“已核对，保留我的修改”后保存E：服务端保存E，F成为历史版本。截图 `stage5-conflict-confirmed-browser.jpg`，收据 `stage5-version-conflict-final.json`。
5. 缺旧论文文件的代表性任务显示可理解的错误，原笔记仍可打开。没有自动替换材料、重建全部旧文件或调用模型。截图 `stage5-missing-file-browser.jpg`。
6. `verify_stage5_recovery.py` 使用独立HTTP客户端、无IndexedDB读取任务、版本、来源、PDF和解析状态：正文/版本/来源符合上述结果，PDF SHA256等于材料编号、正文阅读状态就绪；缺文件为404且笔记保留。收据 `stage5-recovery-client-runtime.json`。此验证不是独立浏览器配置/缓存恢复验收。

## 实测发现与修复

浏览器出现429错误。检查源码发现所有闲置历史任务会在启动时逐个查询、每分钟继续轮询；多任务及多个客户端共享Python网关限流，闲置轮询会放大流量。

修改为只轮询当前任务和本地仍待确认的请求；切换任务时立即查询新任务，后台未确认请求仍每3秒恢复。其他客户端在非当前任务创建的请求，会在选择该任务时读取；本改动不提供闲置任务的全局实时通知。

材料处理轮询对400/404停止自动重查；429至少等待15秒，并尊重响应retryAfter。缺文件阅读错误改为简短说明，保留笔记/成果。没有提高或关闭服务端限流。

前端两文件31项通过，含61任务时只轮询当前任务、后台待确认请求持续恢复、新选择任务立即读取、缺记录材料30秒内不重复轮询，以及原有取消/重试/迟到响应与文档交互测试。类型检查和生产构建通过。浏览器修复后当前验收页面无此前的请求恢复错误提示；不据此声称所有并发情形都不会限流。
