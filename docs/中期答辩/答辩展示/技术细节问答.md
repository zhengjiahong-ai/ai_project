# 答辩提问环节：技术细节问答

> 用途：用于中期答辩提问环节。当老师追问“系统怎么实现”“RAG 怎么做”“创新功能背后的技术是什么”时，可按本稿回答。  
> 使用建议：优先背最后的 1 分钟总回答；如果老师追问某个具体功能，再使用对应问题的短答或展开版。

---

## 1. 老师问：你们整体系统是怎么实现的？

可以回答：

> 我们整体采用三层架构：前端是 React，负责 PDF 阅读器和各个功能面板；后端网关是 Spring Boot，负责统一 `/api` 接口和请求转发；核心 AI 服务是 FastAPI，负责论文解析、RAG 检索、大模型调用和各类分析任务。  
> 外部能力主要包括 GROBID、向量检索和大模型服务。GROBID 用来把 PDF 解析成标题、摘要、章节和正文片段；检索模块负责从当前论文中找到相关证据；大模型负责基于证据生成回答、解释、分析和报告。  
> 这样设计的好处是前端、网关和 AI 能力相对解耦，后续扩展或替换某一层都比较方便。

更短版：

> 系统是 React 前端、Spring Boot 网关和 FastAPI AI 服务三层架构。前端负责展示和交互，Java 网关负责统一接口，Python 服务负责论文解析、检索和模型分析。

---

## 2. 老师问：PDF 上传后，你们具体做了什么？

可以回答：

> PDF 上传后，我们不是简单保存文件，而是先调用 GROBID 对论文进行结构化解析，提取标题、摘要、章节和正文片段。  
> 然后我们会对解析结果做清洗和分块，把论文转成后续可以检索和引用的片段。  
> 这些片段会作为 RAG 问答、术语解释、批判性阅读、背景补课和深度研究的基础材料。

更短版：

> 上传后会先用 GROBID 做结构化解析，再清洗和分块，形成可检索的论文片段，供后续问答和分析复用。

---

## 3. 老师问：你们的 RAG 问答怎么减少幻觉？

可以回答：

> 我们不是直接把用户问题交给大模型，而是先从当前论文中检索相关片段。  
> 具体流程是：用户提问后，系统先做简单的意图识别和查询规划，然后优先在当前论文片段中检索证据，再把问题和证据一起传给模型生成回答。  
> 回答中会保留 `rag_sources`，也就是相关来源片段，方便用户追溯回答依据。这样可以减少模型脱离论文自由发挥的问题。

更短版：

> 我们先检索当前论文证据，再让模型基于证据回答，并返回来源片段，所以比直接问大模型更不容易脱离原文。

---

## 4. 老师问：划词解释和普通词典解释有什么区别？

可以回答：

> 划词解释不是单独解释一个词，而是结合当前页面上下文和论文片段来解释。  
> 因为同一个术语在不同领域或不同论文里含义可能不完全一样，所以我们会把用户选中的文本、当前页信息和相关论文上下文一起传给后端，再生成解释。  
> 这样得到的解释更贴近当前论文，而不是百科式定义。

更短版：

> 它会结合当前论文上下文解释术语，而不是只给通用定义。

---

## 5. 老师问：全景翻译是怎么做的？

可以回答：

> 全景翻译是按当前 PDF 页面进行处理的。系统会提取当前页中适合翻译的文本，同时尽量跳过图表、图片和公式区域。  
> 译文生成后，我们会尽量保持与原页面相近的阅读顺序和版面对应关系。  
> 这样用户在阅读原文时，可以同步参考当前页的中文译文，而不是把整篇论文复制出去做一次性翻译。

更短版：

> 全景翻译按页提取文本，尽量保留和原文页面的对应关系，并跳过图表区域，适合边看论文边参考译文。

---

## 6. 老师问：批判性阅读是怎么判断论文贡献和局限的？

可以回答：

> 批判性阅读基于论文结构化内容和检索证据进行分析。  
> 我们会把分析维度固定在贡献、方法、实验和局限几个方面，让模型输出基于证据的真实贡献、薄弱点、夸大风险和缺失证据。  
> 重点不是让模型泛泛总结论文，而是要求它尽量根据论文中的证据判断哪些结论有支撑，哪些地方可能证据不足。  
> 如果证据不足，系统会明确标记，而不是直接编造结论。

更短版：

> 它会围绕贡献、方法、实验和局限做证据化分析，重点识别哪些贡献有证据支撑，哪些地方可能存在夸大或证据不足。

---

## 7. 老师问：你们说的“伪贡献”怎么识别？

可以回答：

> 我们不是直接判断一篇论文是不是“伪贡献”，而是辅助用户发现贡献和证据之间是否匹配。  
> 比如论文宣称有创新，但如果对应的实验、对比或方法差异不足，系统会在批判性阅读中提示可能存在 overclaim risk，也就是夸大风险。  
> 所以它更像是一个证据检查工具，帮助用户发现论文贡献是否真的被实验和论证支撑。

更短版：

> 我们主要通过贡献和证据之间的匹配关系来提示风险。如果论文宣称很强，但实验或方法差异支撑不足，就会提示可能存在夸大风险。

---

## 8. 老师问：背景补课是怎么生成的？

可以回答：

> 背景补课会结合论文主题、关键词、章节结构和相关片段，判断读懂这篇论文需要哪些前置知识。  
> 然后根据用户选择的知识水平，比如入门、一般或进阶，生成概念图谱、学习路径和补课清单。  
> 它不是再次总结论文，而是回答“为了读懂这篇论文，我需要先补哪些基础知识”。

更短版：

> 它会根据论文主题和用户水平生成概念图谱和学习路径，帮助用户补齐读懂论文需要的前置知识。

---

## 9. 老师问：引导式学习为什么设计成五轮问题？

可以回答：

> 我们把论文理解拆成几个比较核心的层次：研究问题、方法创新、方法逻辑、实验依据和局限改进。  
> 这五个维度基本覆盖了从“论文想解决什么问题”到“方法是否可靠、还有什么不足”的理解过程。  
> 用户回答后，系统会结合论文内容给出反馈、掌握度判断和回读建议。  
> 这样设计的目的，是让用户从被动看答案，转成主动回忆和表达。

更短版：

> 五轮问题分别对应研究问题、方法创新、方法逻辑、实验依据和局限改进，用来检查用户是否真正理解论文。

---

## 10. 老师问：深度研究具体怎么运行？

可以回答：

> 深度研究面向开放研究问题。用户输入问题后，系统会先把它拆成 3 到 5 个子问题。  
> 然后每个子问题会调度内部工具，包括当前论文检索、文献库检索、证据判断和报告综合。  
> 最后系统把各个子问题的结果汇总成结构化研究报告。  
> 当前阶段已经完成基本逻辑闭环，包括任务创建、轮询查看、取消和报告展示，后续会继续优化报告质量和任务调度。

更短版：

> 它会把开放问题拆成多个子问题，再调用检索、证据判断和报告综合，最后生成结构化研究报告。

---

## 11. 老师问：深度研究和普通搜索有什么区别？

可以回答：

> 普通搜索更多是返回一批资料，用户还要自己筛选和组织。  
> 深度研究则会先拆解问题，再围绕子问题检索证据，最后把结果组织成结构化报告。  
> 所以它不是简单“找资料”，而是帮助用户把一个开放研究问题推进成可分析、可汇总的任务链。

更短版：

> 普通搜索给资料，深度研究会拆问题、找证据、做汇总，更接近研究问题推进流程。

---

## 12. 老师问：你们的安全防护怎么做？

可以回答：

> 我们把论文正文、页面上下文和 RAG 片段都视为不可信输入。  
> 因为论文文本里理论上可能包含类似“忽略之前指令”“泄露 API Key”“执行命令”等提示注入内容。  
> 所以在进入模型前，系统会对这些内容进行检测和包装，避免论文文本改变系统指令边界。  
> 同时，Trace 只记录阶段状态、耗时、检索次数和截断摘要，不记录 API Key、完整 prompt 或完整论文全文。

更短版：

> 我们把论文内容视为不可信输入，对提示注入做检测和包装；Trace 只记录必要过程信息，不记录密钥和完整 prompt。

---

## 13. 老师问：Trace 是做什么的？

可以回答：

> Trace 主要用于观察系统内部任务执行过程。比如一次深度研究或一次检索，会经过哪些阶段、每个阶段耗时多久、检索了多少次、结果是否被截断。  
> 它帮助我们后续排查问题和优化性能。  
> 但为了安全，Trace 不记录 API Key、完整 prompt、完整论文全文或原始日志，只记录必要的摘要信息。

更短版：

> Trace 用来记录任务阶段、耗时和检索次数，方便调试和优化，但不记录敏感信息。

---

## 14. 老师问：项目和 MCP 有什么关系？

可以回答：

> 当前项目没有把 MCP 作为已上线功能，也没有直接提供对外 MCP server 或 MCP client。  
> 但我们内部已经有工具注册和任务调度的雏形，比如深度研究会调用当前论文检索、文献库检索、证据判断和报告综合等内部能力。  
> 所以后续可以考虑把这些内部工具标准化，并通过 MCP adapter 映射出去。  
> 简单说，MCP 是后续扩展方向，不是当前阶段的核心实现。

更短版：

> MCP 目前是后续扩展方向。当前系统还没有上线 MCP，但内部工具注册和深度研究调度为以后接入 MCP 留了基础。

---

## 15. 老师问：为什么要用 Java 网关，而不是前端直接调用 Python？

可以回答：

> 主要是为了接口统一和系统解耦。  
> 前端只需要调用统一的 `/api` 接口，不需要直接感知 Python AI 服务内部有多少模块。  
> 后续如果 Python 服务拆分、替换模型或调整部署方式，前端接口可以尽量保持稳定。  
> 同时 Java 网关也方便统一做跨服务转发、接口管理和后续权限控制。

更短版：

> Java 网关主要用于统一接口和解耦前端与 AI 服务，方便后续维护和扩展。

## 最推荐背诵的 1 分钟总回答

如果老师问得比较笼统，比如“你们技术上具体怎么做的？”，可以直接答这一段：

> 我们整体是 React 前端、Spring Boot 网关和 FastAPI AI 服务的三层架构。用户上传 PDF 后，系统会用 GROBID 解析论文标题、摘要、章节和正文片段，再做清洗和分块，作为后续检索和分析的基础。RAG 问答不是直接问大模型，而是先从当前论文中检索相关证据，再让模型基于证据回答，并返回来源片段。划词解释和全景翻译也是结合当前页面上下文来做。  
> 在创新功能上，批判性阅读围绕贡献、方法、实验和局限做证据化分析；背景补课根据论文主题和用户水平生成概念图谱和学习路径；引导式学习通过五轮递进问题检查用户理解；深度研究则把开放问题拆成子问题，再调度检索、证据判断和报告综合生成结构化报告。安全上，我们把论文内容视为不可信输入，对提示注入做检测，Trace 只记录必要过程信息，不记录密钥和完整 prompt。
